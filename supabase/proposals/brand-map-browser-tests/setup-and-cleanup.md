## Actual client login and API method

The current application uses session-scoped storage but its shared browser configuration targets the main project. A separate test page must therefore own its Test configuration, verify the expected project before any request, and never import the main `auth/config.js` or the combined portal entry point. A test-local map view may reuse pure display code only after dependencies are reviewed. Full portal integration remains a later phase.

Use only the Test publishable key in the browser. User A and B sign in separately; verify each identity with Auth `getUser` (or its supported equivalent), then send each account's real token with the normal Data API request. Never manufacture JWT claims, sign a token, use a service-role/secret key in the browser, or treat SQL role simulation as real login evidence. Supabase's SDK normally sends the user's Auth token to scope requests. [Supabase Auth](https://supabase.com/docs/guides/auth)

Prefer the Dashboard's supported direct Create User path with auto-confirmed, run-specific disposable email identifiers and no invitation email, subject to confirming the current UI offers this path. Auth Admin creation supports an email-confirmed account; privileged keys belong only on trusted servers. [Supabase createUser](https://supabase.com/docs/reference/javascript/auth-admin-createuser)

The user must enter and submit each new password privately when that step is reached. This handoff is required by the browser-control credential policy; passwords are not requested through chat. No emailed invitation, reset request, magic link, SMTP change, signup-policy change, CAPTCHA bypass or real address is part of the proposal. If a supported no-email creation path is unavailable, report that specific blocker and request a revised method rather than changing Auth settings.

Use two independently opened test tabs with isolated in-memory tokens. Never share an SDK singleton or session between them. Show only synthetic records. The read and write checks in `test-matrix.json` include both directions, direct-table attempts, anonymous calls, forbidden legal review, stale edits, a still-valid token after fixture membership revocation, and the fixture-only disabled portal. Verify rejected writes caused no database change. Unexpected errors or empty UI alone do not count as privacy success.
