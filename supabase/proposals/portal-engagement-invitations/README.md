## Owner's flow

Clients contain engagements. Attorney selects the client/contact already on file and reviews its saved contact email before sending; there is no recipient email input and no Member directory/activity feed. A consultation via Calendly is distinct. New invitees verify identity, choose a password through the Auth invitation flow, and complete the normal acknowledgment/company onboarding before explicitly accepting. Existing Members verify/sign in to their same account and accept. All Client features are included, with separate engagement-record scopes. Acceptance does not replace an engagement agreement.

## Implementation

- Private invitations reference a draft revision and the reviewed legal-client contact. Seven-day, single-use, explicitly accepted; sender must be staff with MFA. Resend revokes the prior invitation and uses a different ID. Expired, revoked, accepted, wrong-email, suspended-account and changed draft/contact invitations cannot be accepted. Auth email must be verified in the server identity table; browser email/metadata is never authority.
- Delivery is the new `engagement-invite` Edge Function, restricted to exact Test project and localhost port 8893, plus `VB_ENGAGEMENT_INVITES_ENABLED=true`. Both existing/new recipient paths use Supabase's existing Auth email service. Only the service-role worker can privately decide which path to use; staff gets the same generic sent/error result. No service credential is exposed to the browser or repository. Staff identity/MFA is rechecked in the database before reservation.
- New identities use Auth `inviteUserByEmail`; existing ones use `signInWithOtp` with automatic signup disabled. The fixed callback is `http://127.0.0.1:8893/login.html?invitation=<UUID>`. Add only the corresponding Test redirect pattern, preserving the existing plain login callback: `http://127.0.0.1:8893/login.html?invitation=*`. Do not broaden hosts/paths or change Site URL. Backend delivery never accepts a browser redirect address.
- A UUID query identifies the invitation; it is not an access credential. Sign-in and signup preserve that ID through private account setup. Acceptance rechecks ID, verified actual recipient, account status, contact and draft under client/draft/invitation locks. It creates engagement/matter/grant atomically, auto-includes all features, and preserves Member data. Already accepted IDs fail; they do not silently return a grant. Read-only page GET and login do not accept anything.
- For an entirely new legal client with no earlier records/memberships, first acceptance establishes its managed scope and future service bindings. Existing mappings, retained marks, history and service configuration are never reassigned to the new engagement. Unmapped existing client records require separate reviewed scope mapping. Existing closed service configurations are not silently reused. Later-engagement activation for an already verified relationship remains an attorney-controlled follow-on; this package does not expose Member discovery or auto-enroll unrelated accounts.
- Draft recipient is derived on the server from saved legal-client contact; stale browser overrides fail. Staff review includes recipient and saved engagement details. Contact edits remain in Client Settings. Draft saving sends nothing.
